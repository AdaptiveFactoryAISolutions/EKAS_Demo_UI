## Shared adapter and acceptance design

1. **Callback intent + committed proof.** Wrap existing normal callbacks/functions with a reusable action descriptor: procedure/action kind, exact object/query ID, intended old→new fields and contextual identity. Only publish a durable action observation after normal persistence succeeds and the committed state matches. Existing `Guide.tsx:38–39` already reads committed audit. No-op/cancel/rejected/provisional writes get zero progress. Reuse adapters at `saveAnswer/pinTo/addKpi`, collection/board mutations, monitor/schedule functions, aliases and actual saved conversation results. Do not synthesize success from button labels.
2. **Separate observation types.** Saved mutation, executed local result, meaningful inspection, preview prepared and clipboard copied need distinct outcomes. The Guide may record an inspection without declaring the workflow, delivery, cause, approval, physical work or certification completed. F012/F045 and F009/F013 share behavior but retain independent procedure identities.
3. **Correlate and persist.** Bind observation to namespace, procedure, object/record ID, exact query/board signature, cutoff/source revision and relevant role/context. On resume re-read them; distinguish the expected version increment caused by this action from unrelated change. Include the real root host: milestone01's explicitly supplied local context is not full root-context acceptance.
4. **Fix receipt lifetime/matching centrally.** `guideModel.ts:30` uses exact kind inclusion, while audit kinds contain dynamic title/IDs; broad text matching is inadequate. `:29–31` consumes every fresh receipt into baseline even on a nonmatching step: handle action-before-step as an already-saved inspectable result or pending correlated observation, never require duplicate creation. `readWalkthrough` requires observed receipt IDs still in current receipts, but `store.ts:349` retains only80 audits: supply durable correlated evidence or explicitly qualify lost evidence; do not promise indefinite progress restoration.
5. **Use one family matrix with per-ID normal targets.** For every nonheld contract: ordinary preparation → actual normal callback → committed result/meaningful inspection → reload → resume. Add invalid/empty/missing/no-op/cancel/write failure, explicit retry exactly once, unrelated concurrent change, scope/role/cutoff/source change, late response, audit rollover and opening a modal during Guide reads. Reuse fixtures/adapters, but execute each ID's real sequence; neither49 descriptions nor family tests replace85 procedural dispositions.
