EKAS INDUSTRY-LEADING UI COMPLETION GOAL
CHAT-FIRST UNIFICATION + ZERO REGRESSION

MISSION

Complete the EKAS UI so it becomes one cohesive, industry-leading manufacturing intelligence product for real plant users.

This is a product-completion goal, not a cosmetic redesign.

The objective is to preserve all working EKAS capabilities while eliminating the fragmentation, confusing navigation, contradictory state, conversational dead ends, hidden workflows, and developer-oriented presentation identified in the independent end-user review.

The final user experience must feel like:

ONE MANUFACTURING EXPERT
ONE CONVERSATION
ONE CONTEXT
ONE INVESTIGATION STATE
ONE EVIDENCE MODEL
ONE ACTION LIFECYCLE
ONE COHESIVE PRODUCT

Do not simplify EKAS by removing capability.

Simplify EKAS by reorganizing and progressively disclosing capability.

==================================================
PHASE 1 — FIX P0 TRUST FAILURES FIRST
==================================================

P0-A: SILENT METRIC / PLANT SUBSTITUTION

Absolute rule:

If EKAS cannot answer the requested metric + plant + entity + period,
it must clarify or refuse.

It must NEVER silently substitute:
- another metric;
- another plant;
- another dataset;
- another investigation.

Examples that must be fixed:

"Why did quality drop?"
must not answer good units from a different plant.

"Why was FPY lower?"
must not answer a downtime bridge.

Before response publication validate:

requested metric
resolved metric

requested plant
resolved plant

requested entity
resolved entity

requested period
resolved period

requested investigation
resolved investigation

If materially different:
CLARIFY OR REFUSE.

Do not publish a confident unrelated answer.

PHASE 6 — ROBUST CONVERSATIONAL INTENTS
==================================================

Support everyday plant-leader follow-ups from any appropriate state:

PHASE 7 — NEXT ACTION AS A FIRST-CLASS SERVICE
==================================================

Every workflow state must expose:

- current state;
- missing prerequisite;
- allowed next actions;
- recommended next action;
- blocked reason.

The user should always know:

WHAT HAPPENED
WHAT IS MISSING
WHAT TO DO NEXT

Examples:

"Maintenance assignment is waiting for acceptance."
[Accept assignment]

"A bounded action is required before approval."
[Review recommended action]

"Approval is required before work can be recorded."
[Request approval]

"No post-action observations are available yet."
[Advance demo time]

This guidance must come from workflow/service state, not hard-coded page copy.
