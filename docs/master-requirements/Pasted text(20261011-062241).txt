EKAS TRUE NORTH — MASTER PRODUCT ALIGNMENT AND COMPLETION DIRECTIVE

PURPOSE

This prompt defines the single canonical True North for EKAS.

Its purpose is to eliminate fragmentation, conflicting interpretations,
partial implementations, UI-only demonstrations, and local optimization.

Every current and future EKAS implementation decision must be evaluated
against this True North.

The objective is NOT to build a collection of screens.

The objective is NOT to build an OEE dashboard.

The objective is NOT to build a chatbot that retrieves metrics.

The objective is NOT to build a workflow tool sitting beside a chatbot.

The objective is to build one cohesive industrial manufacturing intelligence
system in which a user interacts naturally with EKAS as if they were speaking
to a world-class manufacturing expert who can:

- understand the operating context;
- calculate trusted manufacturing facts;
- explain what happened;
- identify where performance was lost;
- inspect governed evidence;
- distinguish facts from hypotheses;
- guide an investigation;
- assign and govern corrective action;
- verify whether the action worked;
- determine whether the improvement sustained;
- preserve evidence and history;
- and connect later to real plant systems through stable APIs.

THIS IS THE TRUE NORTH.

==================================================
THE EKAS PRODUCT VISION
==================================================

EKAS is a CHAT-FIRST MANUFACTURING INTELLIGENCE AND OPERATING SYSTEM.

The primary experience is a natural conversation.

The user should feel like they are speaking to:

"a world expert in manufacturing who knows my plant, my process, my data,
my standards, my history, and my operating priorities."

The user should NOT need to know:

- which database contains the data;
- which service performs the calculation;
- which screen contains a particular workflow;
- which metric ID is being used;
- which document repository contains a PFMEA;
- which backend adapter is currently synthetic or live.

EKAS hides system complexity while preserving evidence, governance and
traceability underneath.

==================================================
THE CORE USER PROMISE
==================================================

A user must be able to say:

"We missed our production goal yesterday. What happened?"

and EKAS must be capable of taking that user through one coherent journey:

The conversation remains the primary control surface.

==================================================
IMPORTANT CURRENT LIMITATIONS
==================================================

The current system must NOT overclaim.

Current limitations include:

1. Training Ask is not yet the universal investigation dispatcher.

2. Training/workbench calculations and Northworks investigation fixtures
   currently represent separate data horizons and must not be silently mixed.

3. The plan gap and theoretical-capacity loss bridge use different baselines.

4. The current speed-loss residual is calculable but not fully attributed
   to governed event/cause evidence.

5. The current feeder-jam case does not prove a speed-loss cause.

6. The current feeder-jam case does not prove a quality-loss cause.

7. Broad speed and quality investigation journeys require their own
   evidence-complete synthetic cases.

8. Hypotheses, ownership, action, evidence and verification currently exist
   across multiple local stores/panels instead of one persistent case record.

9. Before/after association is not automatically causal proof.

10. Financial opportunity is not automatically verified cash savings.

11. Real MES / ERP / CMMS / QMS / historian / document / identity systems
    are not yet the source.

12. Future backend integration contracts are not fully available from Tom.

13. UI acceptance of individual screens does not prove the complete user
    outcome.

14. Passing unit tests does not prove the product journey.

15. Scripted ShowMe playback does not prove an unaided user can operate EKAS.

- active line;

- active job;
- active part;
- part revision;
- operation;
- shift;
- primary period;
- comparison period;

- clarification state.

Changing one dimension must not corrupt another.

Example:

comparison period = February

"Go back to Machine 1"

must not accidentally make February the primary period.

Explicit metric requests override inherited metric context.

"What was FPY?"

must never answer OEE.
