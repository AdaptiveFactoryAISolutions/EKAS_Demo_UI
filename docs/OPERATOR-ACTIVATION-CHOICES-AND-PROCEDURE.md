2. Reviewer supplies an Ed25519 public PEM and its independently verified fingerprint; signing private key never leaves their managed custody. After explicit security-configuration approval, the authorized machine admin creates /etc/ekas owned root:root0755 and installs the verified public PEM as /etc/ekas/activation-review-public-key.pem owned root:root0644 (or stricter non-group/world-writable readable permission). Compare the installed public-key fingerprint to the approved reviewer through the approved independent channel. This is the exact path/ownership checked by this candidate; **no commands were executed here**. Revocation: remove/replace the accepted receipt or approved public key; running authority rechecks their unchanged bytes/expiry and refuses further turns. Provisioning/revocation is a human security operation, not an automatic app mutation.

```json
    "version": 1,
    "kind": "EKAS_INDEPENDENT_LIVE_ACCEPTANCE",
    "artifactSha256": "<64lowercasehex of exact final ZIP bytes>",
    "policySha256": "<64lowercasehex of exact policy UTF8 file bytes>",

    "scope": "synthetic-openai-demo",
    "status": "accepted"
  },
  "signature": "<base64 Ed25519 signature of UTF8 JSON.stringify(payload)>"

```

Sign exactly the parsed payload object's JSON.stringify serialization, preserving its property order; verification calls node:crypto.verify(null, UTF8serializedPayload, installedApprovedPublicPEM, decodedSignature). The reviewer uses their own managed signing key handle; the demo/agent does not read or generate a real signing private key. SHA fields are computed from the final actual files, never placeholders. Source tests generate transient test-only pairs; those do not authorize anything. Byte changes to policy/receipt/identity or active executables, changed anchor, expired review/pricing or held budget refuse. Accepted-review report and key fingerprint provenance accompany the receipt through the permitted channel; no broader product/production/Tom/backend/financial/licence acceptance is implied.
